  MECHANISM
  --------
  applyTaskContractToCompactedMessages() computes the contracted request with
  the EXISTING estimator (estimateRequestInputTokens) and compares it against
  the EXISTING effective limit (resolveEffectiveMaxInputTokens + the user
  operating ceiling, which may only REDUCE the limit). When the contracted
  request would exceed that limit, it throws TaskContractBudgetError:

    - the mandatory instructions are never truncated;
    - no oversized request is produced by the transformation;
    - the sidecar is not persisted with a partial contract;
    - the configured ceiling is never relaxed (applyUserContextCeiling can
      only lower the operating capacity);
    - preparation fails before provider dispatch, so an un-contracted
      summary can never be presented as a valid continuation.

  The hermetic controls assert:
    - oversized contract -> TaskContractBudgetError;
    - user ceiling below model capacity -> TaskContractBudgetError and zero
      sidecar writes;
    - pre/post-compaction system prompt differences -> the final prompt is
      used for the budget decision;
    - the LocalRuntimeHost production prepareTurn receives the configured
      96K user ceiling and writes no compaction sidecar when the guard fails.
