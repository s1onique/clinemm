CRITICAL SAFETY TEST -- N2 PERSISTENT DESCENDANT (REAL_PROCESS)
------------------------------------------------------------------------

Case: `G2 -- a persistent descendant keeps the owned group alive and is
NEVER reconciled`

Setup: a 30-second descendant in the ORIGINAL owned PGID; the shell
exits naturally; the reconciliation schedule is given a finite budget
(`maxAttempts: 4`, `horizonMs: 1200`, `intervalMs: 100`) and the
observation window extends well beyond it.

Result:
  * `descendantIdentityVerified` = true (the descendant is positively
    identified as a member of the ORIGINAL PGID)
  * `immediateLiveness` = "alive" (kernel truth at the finalize
    boundary)
  * the manager's production terminal state = "containment_failed"
  * `laterLiveness` = "alive" (the group is demonstrably alive AFTER the
    descendant's own lifetime would have to be re-checked)
  * `reconciliation` = undefined
  * `reconciliationEvents(events)` = length 0
  * `terminalCommits` = 0
  * `containmentFailures` = 1 (the ORIGINAL incident is retained)

  After the FULL reconciliation observation horizon:
    -> no reconciled clean terminal
    -> the controller retains `containment_failed`
    -> C10 remains HELD

PASS: `HALT_UNSAFE_CONTAINMENT_RELEASE` is NOT triggered. The
persistent-descendant control is conserved.

------------------------------------------------------------------------
NON-RELEASE FACTORS (structurally impossible to satisfy)
------------------------------------------------------------------------

The following can NEVER release a containment obligation, because the
reconciliation requires a fresh `gone`/ESRCH verdict from the
production postcondition probe of the ORIGINAL owned PGID:

  root process exited               -> no `gone` certificate
  active manager map empty           -> no `gone` certificate
  child stdio closed                 -> no `gone` certificate
  historical job older than timeout  -> no `gone` certificate
  EPERM from kill(-pgid, 0)          -> classified `eperm`, blocked
  unknown postcondition              -> classified `unknown`, blocked
  empty ps membership                -> NOT consulted by production
  unmatched jobId                    -> the pending entry is keyed by
                                         jobId; a non-matching entry is
                                         never reconciled
  unknown owner                      -> fail closed
  stale session or task epoch        -> the launch-time owner id is
                                         preserved verbatim

The `ps`-membership snapshot is a READ-ONLY DIAGNOSTIC in the NEPCR01
observation harness only. The PRODUCTION reconciliation never consults
it; it consults `process.kill(-pgid, 0)` through the existing
`defaultTerminalPostconditionProbe` seam.

PRIMARY-PGID INVARIANT
----------------------

The repair does NOT broaden the claim. It proves the disappearance of
the PRIMARY OWNED PROCESS GROUP (the original PGID) and nothing more.
It does NOT claim that no descendant escaped into another group - that
would require independent evidence the ACT does not provide. The
invariant statement is unchanged:

  CLEAN_TERMINAL => authoritative owned primary PGID gone
