ACT-CLINEMM-READ-RESULT-DEDUP-REPAIR01-CORRECTION01 — conservation

Production change (one seam, no new persistence, no tool/authorization change):
  MessageBuilder.projectDuplicateReadResults now splits each locator's read observations
  into CONTIGUOUS RUNS of byte-identical content instead of grouping all observations that
  ever shared a hash. Only the LAST run of a locator is current. Every earlier run holds
  superseded content and is:
    - never projected into a compact reference, and
    - never shielded from the existing 64 KiB stale-read rewrite policy.
  MessageBuilder.buildForApi additionally skips the anchor/reference shielding explicitly
  for obsolete result ids, so the protection cannot be re-granted to superseded content.

Freshness conservation (the corrected P0), verified through real MessageBuilder.buildForApi:
  X -> X -> Y, 40,000-character payloads (two copies cross the 64 KiB threshold)
    A (anchor X) -> "[outdated - see the latest file content]"
    B (duplicate X) -> "[outdated - see the latest file content]"
    C (newest Y) -> full 40,000-character Y payload
    No "same content as earlier read result" marker survives, so nothing points at a
    rewritten anchor.
  X -> X -> Y across a sticky multi-build sequence on one builder instance:
    Same result. The anchor is protected while the content is current and unprotected once
    a later, different observation supersedes it.

First-anchor deduplication is preserved for unchanged content:

    B (superseded Y) -> "[outdated - see the latest file content]"
    C (newest X) -> full 40,000-character X payload
    C does not claim identity with the superseded earlier X.

Final-projection anchor lifetime:
  After aggregate budget processing, every emitted reference is checked against an earlier
  real tool result in the same final projection. If the anchor was removed, truncated, or
  rewritten, the reference is replaced by an explicit unavailable-content notice; no
  dangling reference survives.
