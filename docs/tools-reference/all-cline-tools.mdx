Cline tools are executable functions the model can call while working. The model decides which tool to call, Cline runs it, then returns results back to the model.

## Built-In Tools (ClineCore)

When running through `ClineCore`, these built-ins are available:

| Tool | Description |
|------|-------------|
| `read_files` | Read one or more files |
| `search_codebase` | Search the workspace |
| `run_commands` | Execute shell commands |
| `fetch_web_content` | Fetch web content |
| `apply_patch` | Apply patch/diff edits |
| `editor` | Edit files |
| `skills` | Invoke configured skills |
| `ask_question` | Ask the user for input |
| `submit_and_exit` | Submit a final answer and stop |

A session offers `editor` or `apply_patch`, never both. By default, Act mode offers `apply_patch` to GPT and Codex models and to every model on the OpenAI (`openai-native`) provider, and `editor` to other models; Plan mode offers neither. SDK callers can replace these defaults with the `toolRoutingRules` session option.

<Note>
`Agent` from `@cline/agents` does not include built-ins by default. You provide tools explicitly.
</Note>

## Tool Categories

- **Codebase operations**: `read_files`, `search_codebase`, `editor`, `apply_patch`
- **Execution**: `run_commands`
- **External retrieval**: `fetch_web_content`
- **Skills**: `skills`
- **Human-in-the-loop controls**: `ask_question`
- **Completion**: `submit_and_exit`

## Approval and Policy Controls

Cline can run tools with approval or auto-approval, depending on settings/policies. Typical patterns:

- Require approval for risky tools (for example `run_commands`, write/edit operations)
- Auto-approve low-risk tools (for example read/search operations)
- Disable specific tools entirely when needed

For policy examples, see [SDK Tools](/sdk/tools) and [Permission Handling](/sdk/guides/permission-handling).

## MCP Tools

Cline can also call tools discovered from MCP servers configured in `~/.cline/data/settings/cline_mcp_settings.json`.

MCP tools are loaded alongside built-ins, so Cline can use both local tools and external integrations in one task.

See [MCP Overview](/mcp/mcp-overview) and [SDK Tools → MCP Tools](/sdk/tools#mcp-tools).

## Process Ownership and Cancellation (PGID-only guarantee)

The `bash` tool runs commands through a supervised process group.
ClineMM **owns and attempts to clean up** each CommandJob's primary
process group when the command completes or is cancelled.

A CommandJob is considered **cleanly terminal** only after ClineMM
establishes that the primary PGID is gone — verified by probing the
process group after the supervised process has exited. If that
postcondition cannot be established (for example: the probe returns
`EPERM` because the kernel refuses to signal the group, or the
probe finds the group still alive, or the group cannot be
addressed), the job terminates as `containment_failed` and ClineMM
surfaces a runtime incident.

What this guarantees:

> A cleanly terminal CommandJob implies its primary owned PGID is
> gone.

What this does **not** guarantee:

> ClineMM does not guarantee cleanup of processes that have left
> the CommandJob's primary process group by any mechanism.

Mechanisms that leave the primary group include, but are not
limited to:

- `setsid()` and any other API that creates a new session /
  process group.
- `setpgid()` / `setpgrp()` moving a process to another process
  group.
- Node child processes spawned with `detached: true` that
  establish independent process ownership.
- Python `subprocess.Popen(..., start_new_session=True)` and
  equivalent `start_new_session=True` flags.
- Double-fork daemonization.
- `nohup`, `disown`, and other shell patterns that ultimately move
  the process out of the owned group.

In any of these cases the descendant is no longer reachable by
signalling the CommandJob's leader PGID, so ClineMM does not kill
it on cancellation. ClineMM does **not** compensate by killing
processes based on UID, executable name, command text, or age;
doing so would be incorrect on a shared system. A `process.kill(-pgid, 0)`
probe returning `ESRCH` is the kernel's "no process exists in that
PGID" signal and is consistent with this model: it is an existence
result for the addressed PGID, not a universal descendant
guarantee.

A `⚠ N` glyph in the task header indicates the number of
**observed** primary-PGID cleanup failures ClineMM has recorded in
the current task session. A `⎇ N` glyph indicates the number of
currently active ClineMM-owned CommandJobs. Hover either glyph for
the full semantics.

## Legacy Tool Names vs Current Runtime Tools

Some older docs/examples reference XML-style names like `read_file`, `replace_in_file`, `execute_command`, or `use_skill`. Current SDK/ClineCore runtime uses the built-in tool names listed above (`read_files`, `apply_patch`, `run_commands`, `skills`, etc.).
