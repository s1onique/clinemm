THE DEFECT THIS EXPOSES
----------------------------
The production SDK mints TWO run identities for ONE run:
  - AgentRuntime    : agent-runtime.ts:1767  this.state.runId = createUID("run")
                    -> carried by EVERY model-request observation
  - SessionRuntime  : session-runtime-orchestrator.ts:1151
                    this.activeRunId = run_${Date.now()}_... ;
                    -> carried by the RUN-TERMINAL observation

The witness asserts they really are different:
  expect(requestRecord?.runId).not.toBe(terminalRecord?.runId)
  -> that assertion PASSED, so the two identities are real.

With the pre-CORRECTION01 scope, the retained snapshot contained ONLY the
run-terminal record. The artifact said "the run failed" WITHOUT saying WHY —
precisely the observability gap this ACT exists to close.

THE REPAIR
------------
The scope is now keyed on the SESSION (which BOTH boundaries carry) and
admits a record when it shares the session AND either the run id or the
model request id. The session id remains a MANDATORY part of the join,
so two concurrent sessions still cannot contaminate each other
(witness T14).

NOTE: unifying the two run identities would mean changing the runtime's
run id, which changes the run result's runId — a PRODUCTION SEMANTIC
change that is out of this ACT's conservation scope. The scope-based join
achieves the same correlation WITHOUT touching production semantics.
