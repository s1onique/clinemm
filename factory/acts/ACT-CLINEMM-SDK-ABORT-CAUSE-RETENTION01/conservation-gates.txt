  Cancellation semantics                      UNCHANGED (abort() still aborts the same signal)

  The ONLY behavioural additions to the agent runtime are:
    - `abort(reason, origin?)` gains an OPTIONAL second parameter.
      Existing callers are unaffected: an omitted origin defaults to
      "unknown" (the agent runtime) and the orchestrator's public abort()
      defaults to "explicit_abort_request". The abort SIGNAL, the abort
      ERROR, the task-lifecycle telemetry event and the run result are
      byte-for-byte unchanged.
    - `observeRunAbortRequested(...)` — a new fire-and-forget, try/catch
      wrapped observation. It cannot change the abort.
    - `describeObservedProviderError(...)` — a pure function that BUILDS a
      payload. It is spread into an existing observation payload; it does
      not touch the error, the request, or the retry decision.

PERFORMANCE CONSERVATION
------------------------
  Disabled path performs NO diagnostic I/O.
    The recorder's enable bit is consulted at observation time: with
    tracing OFF, `recorder.record()` returns `undefined`, so
    `observeSdkAbortCauseRecord(undefined)` and
    `captureSdkAbortCauseSnapshot(undefined)` are both no-ops, and the
    dump command is never invoked.
    Witness: T9 (recorder disabled -> 0 records, 0 snapshots).
  No per-token persistence.
    The retention module retains ONLY the request-lifecycle and terminal
    boundary kinds (model_request_start / _finish / _error / _abort /
    run_abort_requested / run_terminated). Tokens, SSE chunks and tool
    events are NOT retained.
  No synchronous disk write in the provider streaming path.
    The observation calls are synchronous and in-memory. The disk write
    happens ONLY in the explicit operator dump command.
  Bounded work.
    At most 64 events and 256 KiB per snapshot; at most 8 snapshots.
