NEW LIVE FACT FOR THIS ACT (operator directive):

    The old CPU profiler REMOVAL_TRIGGER is overridden. The CPU
    profiler is RETAINED as a diagnostic substrate (default-off,
    dogfood-only, bounded, removable only via a bounded-removal
    ACT). Re-arming the profiler on demand is cheaper than re-
    deriving its production seams.

DESIRED NEW EVIDENCE TYPE FOR THIS ACT:

    TERMINATION-AUTHORITY CLASSIFICATION (TA1..TA6)
    Whether the JS path observed a normal exit event, the operator
    observed a parent-side termination, a macOS crash report exists,
    or the operator observed a resource-exhaustion report.
    NOT a JS CPU attribution. NOT another profiler capture.

EPISTEMIC GAP THIS ACT FILLS:

    LIVE capture showed the host was overwhelmingly idle before
    death. VS Code's reactive CPU profiler attached AFTER the
    stall -- too late. Our pre-armed CPU profiler confirmed CP5:
    no dominant JS hot leaf.

    So this ACT pivots from JS CPU hotness to TERMINATION
    AUTHORITY:

        LIVE extension-host death
          -> who/what terminated the process?
          -> explicit JS/process exit?
          -> native crash?
          -> host/watchdog/external kill?
          -> OOM / resource exhaustion?
          -> unknown

WHY A NEW DIAGNOSTIC INFRASTRUCTURE (not extending the CPU profiler):

    The CPU profiler captures pre-FAILURE segments. The
    termination question requires capturing what happened AT AND
    AFTER failure -- including the parent-side signals the in-
    process host cannot see.

    A separate, default-off, dogfood-only process witness is the
    load-bearing seam for this ACT.
