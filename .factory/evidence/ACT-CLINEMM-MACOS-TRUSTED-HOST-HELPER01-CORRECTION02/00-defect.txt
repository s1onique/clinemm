REVIEWER (macOS launchd engineer, protocol reviewer, Factory reviewer):
  HALT_HOST_HELPER_PROTOCOL_CORRELATION_REGRESSION

P0 (protocol conservation):
  CORRECTION01's C helper no longer echoes request_id in successful
  responses, even though request/response correlation is part of the
  frozen protocol contract.

  The parent protocol (tools/macos-host-helper/protocol.ts) says:

    export interface ResponseEnvelope =
      | {
          readonly version: 1
          readonly request_id: string
          readonly ok: true
          readonly service: typeof SERVICE_NAME
          readonly pid: number
          readonly uid: number
        }

  CORRECTION01's C helper instead emits:

    snprintf(buf, sizeof(buf),
      "{\"version\":1,\"ok\":true,\"service\":\"clinemm-host-helper\","
      "\"pid\":%d,\"uid\":%d}\n",
      ...);

  No request_id. Worse, client.ts has adapted to the regression by
  defining HealthResponse without request_id, and the new tests only
  check ok, version, service, pid, and uid.

  That is exactly the sort of production-contract drift the correction
  cycle must not introduce.

P1 (permissive fallback):
  CORRECTION01's fallback condition:

    if (rc == 0 && cnt >= 1) { use_activated_fd(); }
    else { fallback_self_bind(); }

  Apple documents three relevant failures from launch_activate_socket():
    ESRCH:   caller is not managed by launchd
    ENOENT:  named socket is not present in the caller's launchd plist
    EALREADY: socket was already activated

  Only ESRCH represents the intended manual/dev situation where self-
  binding makes sense. If a launchd-managed process gets ENOENT because
  the plist name is wrong, or EALREADY because activation happened
  twice, silently self-binding hides a real launchd configuration defect.
