EVIDENCE — what InstancesStore.write would need (Foundation has it)
--------------------------------------------------------------------
File: apps/vscode/src/sdk/instance-store/contracts.ts
File: apps/vscode/src/sdk/instance-store/instances-store.ts

InstancesStore.write(instance) exists and accepts arbitrary
opaque `instanceId` strings. The bootstrap primitive could
write a new instance WITHOUT changing any Foundation code.

The only missing piece is a CALLER that:
  (1) derives the instance from the legacy/current config,
  (2) names it (opaque id generation),
  (3) persists the physical credential under the instance
      namespace via StateManager.setInstanceSecret(...),
  (4) calls InstancesStore.write,
  (5) creates the ModelProfile referencing the new id,
  (6) binds the active task's HistoryItem.activeProfileId,
  (7) publishes state.

No such caller exists on the exact HEAD.

EVIDENCE — what saveCurrentAsProfile (helper) expects
-----------------------------------------------------
File: apps/vscode/src/sdk/profile-store/owner.ts

saveCurrentAsProfile(store, name, providerInstanceId, modelId)
    — REQUIRES a non-null providerInstanceId argument.
    — Does NOT bootstrap one.

The helper is correct for its purpose (creating a profile
given a known instance). It is the wrong abstraction for
the first-run case, where the instance does not yet exist.

EVIDENCE — what would have provided this previously
---------------------------------------------------
The REMOVED code path (per the C3 fix comment at
saveCurrentAsModelProfile.ts:54-64):

    Object.values(instances).find(i => i.providerId === providerId)

That fallback was unsound (providerId collapse across multiple
same-provider instances), but it WAS the only path that could
answer "What instance is the current config?" for a first-run
user.

Removing it was correct. Replacing it with a typed bootstrap
that preserves the no-collapse invariant is the work this ACT
exists to do.

AMENDMENT NOTE (2026-09-07)
------------------------------------------------------------------------
The atomic ordering described above (six steps, ending with task
binding) is amended to a two-phase model:

  definition commit (durable):
    (1) read current/legacy ApiConfiguration
    (2) resolve physical credential from CURRENT_CONFIGURATION
        authority (NOT the new instance-secret namespace — the
        namespace does not yet exist)
    (3) generate opaque instanceId
    (4) derive InstanceSecretName = nameFor(instanceId)
    (5) setInstanceSecret(name, physical-credential)
    (6) InstancesStore.write with credentialRef.name === name
    (7) ProfilesStore write referencing new instanceId
        → profile creation is the durable commit boundary

  post-commit composition (best-effort):
    (8) writeActiveProfileIdToHistoryItem — may fail independently
    (9) postStateToWebview — may fail independently
        → if either fails, return CREATED_BINDING_FAILED instead
          of a generic failure (truthful success-with-warning)

The Foundation primitives remain unchanged:
  - InstancesStore.write supports arbitrary opaque instance ids
  - setInstanceSecret / getInstanceSecret form the namespaced
    secret authority
  - ProfilesStore write + parser unchanged
