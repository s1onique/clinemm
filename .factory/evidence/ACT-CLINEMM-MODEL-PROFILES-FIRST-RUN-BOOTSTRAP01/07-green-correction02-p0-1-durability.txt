WHAT WENT GREEN
---------------
P0-1: today `CREATED` could describe a profile whose secret
hadn't hit disk. The bootstrap captured `setInstanceSecret`
but did NOT await the persistence barrier before returning
CREATED. The fix is an explicit persistence barrier between
the cache-mutating step and the commit-boundary step.

FREEZE (BOOTSTRAP_COMMIT_MODEL sub-rule, NEW 2026-09-08)
--------------------------------------------------------
  PROFILE_COMMIT IMPLIES REFERENCED_SECRET_ALREADY_DURABLE

  Before the instance and profile writes, the bootstrap MUST
  await a persistence barrier that drains setInstanceSecret's
  debounced flush so that the referenced physical secret exists
  physically in secrets.json before the profile record
  references it.

A flush failure surfaces as INSTANCE_WRITE_FAILED with a
human-readable message. Per the existing BOOTSTRAP_COMMIT_MODEL
freeze we do NOT roll back the in-memory secret write; the
user re-tries, tolerable garbage-tolerance applies.

WHY THIS IS A REAL FIX AND NOT A STUB
-------------------------------------
The test uses the REAL StateManager.setInstanceSecret (which
schedules a 500ms debounced flush) and the REAL
StateManager.flushPendingState (which cancels the debounce
and forces an immediate write).

Before the fix, the bootstrap would have called
`setInstanceSecret` (cache + debounce) and then immediately
`instancesStore.upsert` + `profilesStore.upsert`, returning
CREATED before secrets.json was written. With the fix, the
`await flushInstanceSecrets()` barrier drains the debounce
BEFORE the instance/profile writes, so the secrets.json entry
exists by the time CREATED is returned. The test exercises the
post-CREATED read directly to assert this.
