WHAT WENT GREEN
---------------
P0-2: today's `captureConnection` left `connection.headers`
absent for the OpenAI-Compatible provider even when the
legacy ApiConfiguration had `openAiHeaders` populated. The
loss was invisible to B1 (Anthropic fixture) but load-bearing
for OpenAI-Compatible users (LiteLLM, corporate gateways,
per-route routing hints).

FIX
---
Extended `captureConnection` to capture `headers` for the
`openai` (OpenAI-Compatible) provider. The capture path
handles both the JSON-encoded string form (legacy webview
storage) and the plain-object form (in-memory callers,
SDK migration, tests) and emits `connection.headers` as a
`Record<string, string>` when the source has headers.

NEW FREEZE (EXACT_CONNECTION_CAPTURE)
-------------------------------------
  captureConnection emits the exact ProviderConnection shape
  the SDK consumes. For V1 the captured fields are:
    - providerId    (always)
    - modelId       (when present)
    - baseUrl       (when present)
    - headers       (when present, openai only)
  The remaining fields (region, apiLine,
  providerSpecificConfig) remain absent on V1 -- no legacy
  equivalent for BOOTSTRAP_COVERAGE providers.

CAPTURE-OPENAI-HEADERS HELPER (NEW)
-----------------------------------
The helper handles three forms:
  - JSON string: JSON.parse(s) -> Record<string,string>
  - Plain object: returned as-is, validated to be a
    Record<string,string>
  - Empty / undefined / invalid: returns undefined
    (NOT {}, NOT null)

This matches `parseProviderConnection`'s `undefined = "field
not on source"` semantic. The typed projector can then
distinguish "field wasn't on the source" from "explicit
clear" (which would be null).
