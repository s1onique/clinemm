WHAT THE USER SEES
------------------
Empty state message: "No profiles yet. Save your current
configuration to get started."
→ click Save → input clears, message unchanged, no banner.

WHAT THE USER DOES NOT SEE
--------------------------
- That the request actually fired.
- That the request actually failed (and why).
- That the system is REFUSING to guess the provider instance.
- That the only path forward (in the current implementation)
  is to first bind a profile, which… requires creating a
  profile, which… requires a provider instance.

WHY THE DEFECT IS A P0
----------------------
The defect blocks ALL first-run usage of the Model Profiles
feature. The chat-label picker is the primary user-facing
surface; the Settings section is the only management surface.
A user with a working legacy/current API configuration cannot
promote that configuration into a profile.

WHY THIS WAS NOT CAUGHT EARLIER
-------------------------------
- The MPWC01 C3 fail-closed fix
  (`ACT-CLINEMM-MODEL-PROFILES-PRODUCTION-WIRING01-CORRECTION01`)
  correctly removed the unsafe `providerId === providerId`
  fallback in `saveCurrentAsModelProfile.ts`.
- The fix landed behind C3/C4 source-check witnesses and a
  typed-foundation composition witness.
- But the C3 RED/GREEN scope was "did the unsafe fallback
  go away" — NOT "can a first-run user succeed end-to-end".
  The full end-to-end path was not exercised in any test
  because the tests assumed an existing bound profile (or
  exercised the typed apply path directly).
- The defect only manifests when:
    (a) profiles = []
    (b) no bound profile
    (c) no existing ProviderConfigurationInstance
    (d) a legacy/current API configuration IS available

  This is the FIRST-RUN state — exactly the state a fresh
  install puts the user in.
