SECRET-SENTINEL SCAN — profiles.json / instances.json / webview payloads
==========================================================================

Recon §18 froze the security invariants:

  profiles.json contains raw secret          = FORBIDDEN
  instances.json contains raw secret         = FORBIDDEN
  webview state contains raw secret          = FORBIDDEN
  RPC result contains raw secret             = FORBIDDEN

PROFILES.JSON SCAN
------------------
Files inspected:
  apps/vscode/src/sdk/profile-store/contracts.ts
  apps/vscode/src/sdk/profile-store/profiles-store.ts
  apps/vscode/src/sdk/profile-store/session-binding.ts
  apps/vscode/src/sdk/profile-store/profile-application.ts
  apps/vscode/src/sdk/profile-store/webview-summary.ts

Sentinel set (from DEFAULT_SECRET_SENTINELS in webview-summary.ts):
  sk-, Bearer , sk-ant-, sk-proj-, x-api-key, api_key,
  apiKey, credentialRef, headers, x-auth-token,
  x-goog-api-key, instance:

Each profile is constructed in tests using only:
  profileId, name, providerInstanceId, modelId
No test data contains any sentinel.

Production source uses:
  - INSTANCE_SECRET_NAME_PATTERN  = /^instance:.+$/
  - nameFor(instanceId)           = `instance:${instanceId}`
  These references are the SECRET-NAMESPACE CONSTANTS, not actual
  secret values. The literal "instance:" appears ONLY in
  contracts that namespace the credential storage.

WEBVIEW PAYLOAD SCAN
--------------------
The ModelProfileSummary projection (webview-summary.ts) has a
machine-enforced sentinel scan that throws if any DEFAULT_SECRET_SENTINEL
substring appears in the JSON-serialized payload.

Test MPQS01_SENTINEL_SCAN_THROWS_ON_LEAK demonstrates the scan
catches a fixture secret injected via a profile name.

Test MPQS01_SERIALIZATION_CONTAINS_NO_SECRET verifies normal
profile summaries contain none of the sentinels.

INSTANCES.JSON SCAN (foundation-level; not modified by this ACT)
----------------------------------------------------------------
The Foundation recon already established that instances.json contains
ONLY:
  instanceId, providerId, displayLabel, credentialRef, connection,
  createdAt, updatedAt
No raw secret is in the file (the credential lives in secrets.json
under the namespaced "instance:" prefix).

RUNTIME SECRET ISOLATION
------------------------
The SdkSessionConfigBuilder.resolve phase (PIIF01 R5 GREEN):
  - reads physical secret via StateManager.getInstanceSecret(name)
  - passes ONLY the resolved value to applyTypedProviderInstanceToConfig
  - never passes the credentialRef.name to the runtime
This invariant is preserved; applyModelProfile calls the same
Builder seam via applyProviderConfigurationInstance.

PROFILE LABEL RENAME DOES NOT CHANGE SECRET KEY
-----------------------------------------------
Per recon §18: "profile label rename changes secret key = FORBIDDEN"

ProfileStore.rename(profileId, newName):
  - only mutates the profile.name field
  - profileId, providerInstanceId, modelId unchanged
  - underlying credential (named `instance:<providerInstanceId>`)
    remains in secrets.json with the SAME key

Test MPQS01_RENAME_CHANGES_NAME_NOT_ID verifies this.

QUICK-SWITCH WRITES CREDENTIAL = FORBIDDEN
-------------------------------------------
applyModelProfile never calls:
  - setInstanceSecret
  - setSecret
  - StateManager.setGlobalState on any secret key
Only:
  - readInstance (read)
  - getInstanceSecret (read)
  - writeTaskHistoryItem (writes HistoryItem, no secrets)
  - postStateToWebview (publishes projection, no secrets)

Test MPQS01_QUICK_SWITCH_NO_DEFAULT_MUTATION confirms the
defaultModelProfileId global state key is NEVER touched by
applyModelProfile.

VERDICT = SECRET_ISOLATION = GREEN.
