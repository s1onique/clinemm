NON-SINGLETON MANAGER (verified)
================================================================

A `CommandJobManager` instance is NOT a singleton. Every
`VscodeSessionHost.create(...)` call site in `SdkController.ts`
instantiates a fresh manager. The active session host is the one wired
into `activeSession.sdkHost`; the others are temp hosts for transient
operations.

The `activeSession.sdkHost` is therefore the authoritative reference
for the Q5 guard. If `VscodeSessionHost` is disposed and replaced
mid-flight (e.g. session rebuild, mode switch), the OLD manager's
state is lost (the OLD manager's `active.delete` happens inside
`dispose()`); the NEW manager is empty.

This is the LA2 / LA5 risk surface.

DETERMINISTIC RED TARGET (per ACT sec 6)
================================================================

Production assertion shape for the RED:

  status(jobId).state === "running"
  AND
  guardManager.getActiveJobOwnershipSnapshot() does not contain jobId

Production API equivalents:

  - manager.status({jobId, waitMs: 0}) → ok=true, snapshot.state="running"
  - activeManager.getActiveJobOwnershipSnapshot() returns []  (or
    omits the target jobId)

The current code can reproduce the contradiction in unit tests by
constructing TWO `CommandJobManager` instances: one that owns the
job (start + status path) and one that does NOT (Q5 guard path).
The diagnostic identities (`managerInstance`, `hostInstance`) are the
load-bearing test seam.
