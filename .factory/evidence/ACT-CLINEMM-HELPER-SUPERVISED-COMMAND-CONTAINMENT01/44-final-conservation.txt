CRASH BEHAVIOR CLASSIFICATION:
    Extension host dies, helper remains.
    The helper's current architecture holds job state in
    process-local memory. When the host dies, the helper
    continues to run (LaunchAgent lifecycle is independent of
    the host process). However, the helper has no peer → job
    mapping that survives host death; it only knows about
    jobs whose owning client has connected at least once.
    After host death, the helper retains the PGID + start_us
    bindings for those registered jobs. A subsequent
    terminate-owned request from a new host cannot reclaim
    those jobs (the client_token is lost with the dead host).
    The PGID-leading PIDs may still be terminated by an
    operator via the helper's process-group.terminate-owned
    method, IF the operator presents a valid client_token,
    which they don't have.
    HOST_CRASH_CONTAINMENT = POSSIBLE for inherited PGID
        (operator can manually walk known PIDs and the helper
        will kill -pgid on request from any client with valid
        client_token — but the operator doesn't have one)
    HOST_CRASH_CONTAINMENT = NOT_SUPPORTED for descendants
        that have escaped the inherited PGID (none of A/B/C
        reach them in the first place; the helper's authority
        is bounded by registered PGIDs)
