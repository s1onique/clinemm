  - Per-field validation (regex / path / extension checks) runs
    in the parser, NOT in the handler — fail closed without
    a subprocess round-trip (protocol.ts:218-264).
  - request_id correlation: every response carries the same
    request_id as the request (envelope buildOkResponse /
    buildErrorResponse). Adversarial request_ids are round-tripped
    safely because the server treats them as opaque strings.

    plist Sockets dict).
  - LaunchAgent activation: server.ts:184-191 uses

RECONCLUSIONS=
  1. The bash executor's `spawn(..., {detached: !isWindows})` IS
     the real production command seam. The CommandJobManager
     wraps it with deadline / wait-budget / id / snapshot.
     This ACT's RED must drive CommandJobManager.start(...) with
     a long-lived child, not a separate node -e analog.
  2. The real cancel seam is CommandJobManager.cancel(jobId).
  3. Termination reaches the kernel through ONE place:
     process.kill(-childPid, signal). That is where the EPERM
     (if any) is swallowed by the current try/catch — the bug
     surface for this ACT.
  4. The host helper's authority surface is the C LaunchAgent
     helper at tools/macos-host-helper/native/helper.c. It
     already speaks the posix_spawn + setpgid + kill(-pid, ...)
     idiom for its OWN testbed runner. The pattern is proven
     there — that is exactly the substrate capability that
     VSCodium-sandboxed extension host lacks.
  5. The helper currently exposes only {health, testbed.*}.
     Adding process-group.terminate-owned requires:
       - ALLOWED_METHODS += "process-group.terminate-owned"
         (and a paired register method)
       - FORBIDDEN_REQUEST_KEYS unchanged (no shell/argv/cmd
         is ever accepted)
       - per-method required fields with opaque token only
       - C-side dispatch in helper.c
       - registration lifecycle owned by helper process memory
