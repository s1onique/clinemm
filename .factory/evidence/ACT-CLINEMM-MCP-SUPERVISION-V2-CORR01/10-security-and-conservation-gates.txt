THE TWO CORRECTIONS, AGAINST THE REVIEW'S TABLE
-------------------------------------------------
  P0-1 - THE FINGERPRINT
    The encoding is now canonical and injective:

      JSON.stringify([operation, sessionId, expectedEpoch,
                      expectedRunId ?? null, text ?? null])

    A JSON array is self-delimiting, so no two distinct field tuples
    can produce the same string. The ledger STILL stores only a
    SHA-256 fingerprint - never the feedback text.

    The ledger STILL NEVER stores the feedback text, so a ledger dump
    still cannot leak task content.

    The operation discriminator is still part of the encoding, so one
    request id still cannot be reused across the two operations.

  P0-2 - THE LIFECYCLE PRELUDE
    The canonical prelude now lives in ONE shared private method,
    `performCanonicalTurnStart`. The ordinary UI route and the MCP
    supervision route BOTH call it, so they cannot drift apart again.

    The two routes differ ONLY in the response type they forward:

      UI route   -> responseType: this.task?.taskState?.askResponse
                   (the UI IS the approval authority)

      MCP route  -> responseType: undefined
                   (MCP feedback MUST NOT be able to answer an
                    approval - LC-3 pins this against a REAL TaskProxy
                    that really does persist "yesButtonClicked")

    The UI route was NOT weakened: LC-4 proves it still forwards the
    persisted response type.

THE FINAL INSTRUCTION, HONOURED
---------------------------------
  Codex may request execution, feedback and cancellation, but ClineMM
  remains the sole authority for task execution, tool approval,
  background-job containment and terminal completion.

  * The feedback route CANNOT answer an approval: the response type is
    an explicit `undefined` and the seam rejects feedback outright
    while `awaiting_approval`.
  * The feedback route now performs the SAME lifecycle as the
    operator's own composer, so a completed or resumable task
    re-enters the correct Elm / C9 / C10 lifecycle.
  * The cancellation route IS the webview's own Cancel path.
  * The terminal completion authority is untouched: a late
    cancellation returns `already_terminal` and never overwrites a
    committed completion.
