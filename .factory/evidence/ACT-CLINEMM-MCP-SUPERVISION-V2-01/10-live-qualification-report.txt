STEP 2 - THE LIVE FIXTURE (C9)

  Use a FRESH DISPOSABLE fixture directory inside `codium-clinemm`.
  NO real production repository. NO secrets. NO destructive commands.
  NO YOLO / auto-approval changes.

  Codex Desktop then performs, in order:

   1. `clinemm_capabilities`
      Expect the READ-ONLY projection to list EXACTLY two operations
      unless the mutation grant is armed. Confirm the capability payload
      before arming anything.

   2. Arm the mutation grant in the UI (the operator's own action).

   3. `clinemm_start_act`
      Capture the accepted `sessionId` and the run identity.

   4. `clinemm_get_run`
      Observe the task. Record the CURRENT `expectedEpoch` - it is the
      conversation epoch reported by the run, NOT a UI sequence number.

   5. `clinemm_send_feedback`
        {
          "requestId":     "<unique>",
          "sessionId":     "<the captured session id>",
          "expectedEpoch": <the current epoch>,
          "expectedRunId": "<the captured run id>",
          "text":          "Please run the focused test."
        }
      Expect `accepted` (or `queued` WITH a `queuedPromptId`).

   6. Confirm the SAME task received the message ONCE. Inspect the
      conversation of the captured session - not a new task.

   7. Start a SEPARATE cancellable run (or a continuation) under the same
      authorized workflow.

   8. `clinemm_cancel_run` - ONCE.
        {
          "requestId":     "<unique>",
          "sessionId":     "<the captured session id>",
          "expectedEpoch": <the current epoch>,
          "expectedRunId": "<the captured run id>"
        }
      Expect `accepted` (the lifecycle outcome - NOT proof the run stopped)
      or `already_terminal`.

   9. REPLAY the SAME cancellation request (same requestId, same payload).
      Expect the SAME recorded outcome, and verify NO second cancellation
      effect occurred.

  10. Verify NO foreign task was affected. The operator retains the
      normal UI approval and Cancel controls throughout.

  DO NOT rely on an assistant completion message as proof of authoritative
  completion. Use the published TaskHeader phase and the existing
  lifecycle diagnostics.

  The operator must additionally observe, for the cancellation:
    - the background-job containment state (a background command that
      remains active must NOT be reported as "cancelled"), and
    - that a late cancellation never cancelled a replacement task.
