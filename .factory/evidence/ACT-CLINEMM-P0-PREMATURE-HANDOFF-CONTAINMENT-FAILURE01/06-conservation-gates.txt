## Notes on rules that are conserved rather than newly asserted

- PHCF-04 and PHCF-05 were already correct in the pre-repair code and REMAIN correct.
  The tests assert them so the repair cannot regress them. They were NOT reported
  as defects.
- PHCF-09 / PHCF-14: the repair introduces NO new error state and NO new wake
  mechanism. The containment failure is already represented by the EXISTING
  canonical task/runtime error authority (the `command_containment_failed`
  runtime-error incident -> `TaskTelemetryTracker.recordRuntimeError` -> the
  task-telemetry WARNING counter) and by the EXISTING per-job
  `backgroundCommandJobStates[jobId] = "containment_failed"` pill, which is
  already published to the webview and already rendered by `ChatRow.tsx:280-289`.
  The repair's only NEW publication is the phase itself.

## The truthful state after a failed containment

The repair does NOT commit `awaiting_followup` (that would misrepresent the
failed containment as a clean handoff) and does NOT leave the phase at
`streaming` (that would leave the UI in a permanent Working state after the
model run genuinely ended).

It commits `resumable` — the EXISTING, established production affordance for
"the run was abandoned before it produced a terminal response, so Resume is the
honest next action" (cancel-path precedent:
`sdk-task-control-coordinator.ts:142-144`, writer
`task-control-cancel-no-active-session`; webview button map
`resumable -> BUTTON_CONFIGS.resume_task` = "Resume Task", in
`webview-ui/src/components/chat/chat-view/shared/buttonConfig.ts:425-426`).

No NEW phase value and no NEW public protocol field were introduced.
