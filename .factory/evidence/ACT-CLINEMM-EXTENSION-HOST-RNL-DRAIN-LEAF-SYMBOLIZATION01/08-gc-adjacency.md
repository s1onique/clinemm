# ACT-CLINEMM-EXTENSION-HOST-RNL-DRAIN-LEAF-SYMBOLIZATION01 — GC adjacency

Generated by `scripts/analyze-cpuprofile-hot-leaves.mjs`.

## Causal-review fix #P0-2 + #P0 (aggregation): two metrics, both honest + invariant-checked

The original analyzer's adjacency algorithm counted the previous/next
non-GC leaf for EVERY GC sample within a contiguous GC run, multiplying
each boundary leaf by the run length. After the first causal review,
the metric was split into two, both labelled:

| Metric                          | Where                                  | Use for?                                              |
|---------------------------------|----------------------------------------|-------------------------------------------------------|
| `gc_run_adjacency` (PRIMARY)    | `result.json.gc_stats.gc_run_adjacency`     | **The only metric used for causal selection.** Independent of run length. |
| `gc_sample_weighted_boundary_exposure` (LEGACY) | `result.json.gc_stats.gc_sample_weighted_boundary_exposure` | Retained under honest name ONLY so prior `total_adjacency` references can be re-anchored. Do not use for ranking.   |

A second-round causal review (#P0 / 2026-09-23, factory causal
reviewer + V8 perf-engineer) caught that `buildTable()` initially
keyed its rows by **sample index**, not by leaf **node_id**. A leaf
adjacent to N different GC runs produced N rows, not one. After that
fix, both metrics are aggregated by `node_id` and the analyzer
enforces three invariants — if any fails, no `result.json` is written
and the run exits with code 3. See *Invariant enforcement* below.


## GC run-length distribution

Reconstructed from the profile's sample sequence: contiguous GC
samples form a single run; the run-length distribution is
computed over all 38,582 samples.

```
runs              = 428
median run length = 31.5    (~4.07 ms at observed 129µs cadence)
p95 run length    = 79      (~10.2 ms)
max run length    = 681     (~87.8 ms)
```

Observation:
- 428 GC runs over the 7,194.81 ms profile (one every ~16.8 ms).
- Median run length = 31.5 samples = ~4.07 ms of contiguous GC.
- p95 run length = 79 samples = ~10.2 ms.
- max run length = 681 samples = ~87.8 ms (longest single GC pause).

This is **NOT a tail-of-single-long-pause** profile: most GC
pressure comes from **many short-to-medium collections**, not
from one pathological event. The 44% sample share is the
cumulative effect of frequent minor-collection churn, consistent
with a sustained high-allocation-rate workload.

The very-long max run (681 samples) IS the same run that the legacy
metric attributed ~284 exposures to each of `observeTurnPhase` and
`emit`. Under the PRIMARY metric that single run contributes 1
boundary exposure at each of those leaves (or 0, if both boundaries
collapse onto a non-tracked intermediate). This is the bias the
expert review correctly diagnosed.

## Invariant enforcement (causal-review fix #P0 / aggregation — REQUIRED)

The `buildTable()` function is now keyed by `profile.samples[i]`-resolved
**leaf node_id**, not by sample index. This is enforced at analyzer
build time by three executably-checked invariants. The analyzer
refuses to emit `result.json` if any invariant fails (process exits 3):

```
(I1) sum_over_rows(gc_before + gc_after) <= 2 * gcRuns
     — each run touches at most 2 non-GC leaves (PRIMARY only;
       LEGACY intentionally violates because it's per-sample)
(I2) each node_id occurs at most once
     — proves aggregation is keyed by leafId, not sampleIdx
(I3) function-level aggregate == sum of its constituent node aggregates
     — no prose arithmetic in evidence; function totals are reproducible
       by summing same-function-name rows in the leaf table
```

Result for this profile (emitted in `result.json.gc_stats.<metric>.invariants`):

```
PRIMARY  gc_run_adjacency                     : I1 sum=855 bound=856 OK=true; I2 unique_node_ids=true; I3 fn_eq_sum_nodes=true
LEGACY   gc_sample_weighted_boundary_exposure: I1 N/A (per-sample);    I2 unique_node_ids=true; I3 fn_eq_sum_nodes=true
```

In words:
- PRIMARY sums to 855, which is `428 × 2 - 1`. That is, 427 GC runs
  contribute 2 boundary non-GC leaves each, and exactly one GC run
  contributes only one (its other boundary is either the start/end of
  the profile or both leaves collapse onto the same `node_id`).
- All 69 PRIMARY rows have distinct `node_id`s (was 661 rows before,
  many duplicates; now properly aggregated).
- For every function present in the table, the per-row sum equals
  the function aggregate. e.g. `e_` rows: 97 + 88 + 81 = 266.
- LEGACY is checked only for I2 and I3 (the column-rename made I1
  inapplicable: a per-sample exposure has no `2 × gcRuns` upper
  bound).


### Why this matters

The previous `buildTable()` keyed by `sampleIdx`, so each leaf that
bounded N different GC runs appeared as N rows with the same
`node_id`. Evidence 09's ranking numbers (e.g. `e_ = 266`,
`Rnl = 69`) were FUNCTION-level sums derived by manually summing
those duplicate rows. That sum was numerically correct (sum over
duplicate-keyed rows = sum over unique-keyed rows for the same
field), but the data structure itself did not represent it. The
function-level ranking was a re-aggregation that the analyzer did
not emit, leaving room for the re-aggregation to drift.

After the fix, the analyzer emits a single table whose primary key
IS the leaf node_id, and a function aggregate is exactly the
group-by over that table. No manual re-aggregation. No drift.

## Interpretation (causal-review refactor)

`e_` (the three `captureContinuationCardinalityAuthorityRecord`
instances) is the most-adjacent function in BOTH metrics: 266 PRIMARY
and 13,333 LEGACY. But `e_` is **conditional on the dogfood diagnostic
profile being ON**; in production OFF it contributes nothing. The
PRIMARY count is real as a CPU-presence indicator; it does NOT
establish that `e_` allocates GC-pressure-causing objects in a production
build.

`Rnl` (xmlTagsRemoval, 69 PRIMARY) and `r_` (normalizeUserInput,
57 PRIMARY) sit on the unconditional prompt-send path. Their
structural allocation capability (one and 2-4 RegExps per call
respectively) is real; their actual byte contribution depends on
call frequency which the CPU profile does NOT measure.

`drain` (54 PRIMARY) and `setWithWriter` (34 PRIMARY) round out the
top. `drain` has conditional object literals + snapshot;
`setWithWriter` has an UNCONDITIONAL eager `record` literal.

The PRIMARY values are close enough (266 / 69 / 61 / 57 / 54 / 45 / 40
/ 36 / 34 — descending) that **the ranking does not single out any
one leaf as the GC pressure owner**. Real allocation data is needed.


## Cautions

PRIMARY adjacency is **not** causation. A JS leaf appearing immediately
before/after a GC run only means that leaf was on the running stack at
the boundary; the leaf may be allocating, may be in a transitive callee
that is allocating, or may simply be in steady-state while allocations
from elsewhere trigger the GC.

PRIMARY adjacency is also **not** an event count weighted by GC burden.
The number of GC-runs a leaf touches reflects only how often that leaf
appears on the stack across all runs; if a run is long (high sample
count), a leaf on its boundary is counted ONCE, not K times. This is
the bounded property the metric intentionally provides.

To upgrade adjacency to causation, allocation must be profiled
directly. The bounded successor ACT
`ACT-CLINEMM-EXTENSION-HOST-ALLOCATION-AUTHORITY01` will use the
correct primitive: Inspector `HeapProfiler.startSampling` /
`stopSampling` with `includeObjectsCollectedByMinorGC = true`,
`includeObjectsCollectedByMajorGC = true` — to capture short-lived
allocation stacks that die young, which is exactly the hypothesis
this profile is consistent with.

## Causal-review verdict (HALT_GC_RUN_ADJACENCY_AGGREGATION_BROKEN → CLOSED)

This file was previously published with a structural defect: the leaf
table was keyed by sample index, so function-level totals were a
re-aggregation that the analyzer did not emit. The defect is now
