## Caveat (post causal-review fix #P0-1)

The "hits" column shown for each ancestor (and for the leaf itself) is
the number of samples where the node was on-CPU, NOT the number of
times the function was called. The chain below describes **which stack
frames were observed** during the profile, not **how many times each
function ran**. The chain does establish the topological shape of the
calling graph (every leaf is reachable only via the listed ancestors in
this profile), but it does NOT estimate call frequency.

For invocation/allocation evidence, the bounded successor ACT
`ACT-CLINEMM-EXTENSION-HOST-ALLOCATION-AUTHORITY01` will capture a
sampling heap profile instead.

---

For each top hot leaf we extract every observed parent path up
to a meaningful runtime boundary. The ancestry chain is built by
walking the parent links in the profile tree, recording each
ancestor with its hitCount, function name, generated location,
and the corresponding authored function (where bound).

The top-down structure is: processTicksAndRejections →
queueMicrotask(emit) → (anon) → drain → ... → setWithWriter /
handleSessionEvent / onSessionEvent. The leaves (Rnl, r_, Gyi, e_)
are observed at the bottom of this stack, typically called from
inside the production code paths.
