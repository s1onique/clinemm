DISPOSITION
-----------

HALT_HOST_BOOTED_FROM_TIME_MACHINE_SNAPSHOT_PROTECTS_USERDATA

The c1-c3 phases of this ACT — clone -> boot -> SSH -> artifact transfer -> e2e
against a real macOS guest — cannot be driven from this shell because **the
host is booted from a Time Machine local snapshot whose APFS volume is mounted
with the firmware `protect` flag.** Every Tart command that touches a network
resource (and therefore touches the per-user NSURLCache at
~/Library/Caches/tart/Cache.db) returns:

    Error: FailedToCreateVmFile

before any guest VM work is attempted. The error originates inside Tart's
NetworkStorageDB, which refuses to write to
/Volumes/UserData/Users/chistyakov/Library/Caches/tart/Cache.db because the
user-data volume is read-only at the APFS layer (mount flag `protect`).

This is a substrate-availability failure, not a defect in the ClineMM Tart
substrate and not a defect in the test infrastructure. The substrate ACT
itself (ACT-CLINEMM-TESTBED-TART-P1-SUBSTRATE01 + CORRECTION01 + CORRECTION02)
is closed and its fail-closed `--backend tart` wiring is provably end-to-end
against the real Tart CLI; the only thing this ACT proves unavailable from
this particular shell is the host's writability.


HOST MOUNT POSTURE (the block)
------------------------------

$ mount | grep -E '/dev/disk3s8|UserData|protect|snapshot'

    /dev/disk3s5 on /System/Volumes/Data (apfs, local, journaled, nobrowse, protect, root data)
    /dev/disk3s8 on /Volumes/UserData    (apfs, local, journaled, protect)
    /dev/disk3s7 on /nix                 (apfs, local, journaled, nobrowse, protect)
    com.apple.TimeMachine.2026-09-18-165509.local@/dev/disk3s8 on
        /private/tmp/snapshot (apfs, local, read-only, journaled, nobrowse, protect)
    com.apple.TimeMachine.2026-10-06-215506.local@/dev/disk3s8 on
        /private/tmp/snapshot (apfs, local, read-only, journaled, nobrowse, protect)

The user-data volume (/dev/disk3s8, mounted at /Volumes/UserData) is itself
mounted with the APFS firmware `protect` flag. macOS also keeps two recent
Time Machine snapshots of that volume mounted at /private/tmp/snapshot — both
read-only and protect. There is no read-write stack mounted at all on
/Volumes/UserData while this shell is active.

$HOME for this process is /Volumes/UserData/Users/chistyakov (getent passwd
chistyakov -> home /Users/chistyakov -> APFS firmlink to
/Volumes/UserData/Users/chistyakov). Every path Tart or the testbed resolves
to inside ~ therefore lands on a firmware-protected, write-rejecting subtree.

DIRECT TART PROBE — NETWORK (cache-write path, THE BLOCK)
---------------------------------------------------------

The single step that would move us into the c1-c3 guest lifecycle is
`tart pull`, and it fails at the NSURLCache write:

  $ HOME=/tmp/clinemm-home TART_HOME=/tmp/clinemm-tart-home \
        tart pull ghcr.io/cirruslabs/macos-sonoma-base:latest

    pulling ghcr.io/cirruslabs/macos-sonoma-base:latest...
    pulling manifest...

    NetworkStorageDB:_openDBReadConnections: failed to open read
        connection to DB @ /Volumes/UserData/Users/chistyakov/
        Library/Caches/tart/Cache.db.
        Error=14. Cause=unable to open database file
    NetworkStorageDB:_openDBWriteConnections: failed to open write
        connection to DB @ /Volumes/UserData/Users/chistyakov/
        Library/Caches/tart/Cache.db.
        Error=14. Cause=unable to open database file
    Failed to retrieve credentials using Keychain credentials
        provider, authentication may fail:
        Failed(message: "Keychain returned unsuccessful status -67674")
    writeDBwithCachedResponse-ERROR:
        (_dbWriteConnection=0x13a005c10) insert SQL stmnt. is nil
        for storage: /Volumes/UserData/Users/chistyakov/Library/Caches/tart

    Error: FailedToCreateVmFile
    (exit 1)

The Keychain -67674 is the same root cause: the TCC-gated
"list-keychain-items-by-name" call inside the security framework cannot
read the user's login keychain because the user-data volume is
firmware-protected and the keychain DB lives on it.

The path Tart resolves for the NSURLCache is the absolute per-user home
(/Volumes/UserData/Users/chistyakov/Library/Caches/tart), independent of
HOME and TART_HOME. There is no Tart configuration knob to redirect this
path; ~/Library/Caches/<bundle-id>/ is the Foundation default for the
process and Tart does not override it. macOS does not expose NSURLCache
redirection by environment variable.


WHY THE HOST IS IN THIS POSTURE
-------------------------------

The mount output shows two simultaneous Time Machine snapshots of
/dev/disk3s8 mounted at /private/tmp/snapshot:

  com.apple.TimeMachine.2026-09-18-165509.local@/dev/disk3s8
  com.apple.TimeMachine.2026-10-06-215506.local@/dev/disk3s8

This is the macOS "booted from a snapshot" safety posture that FileVault +
Time Machine produce when the user (or an external tool) intentionally
rolls the boot volume back to a previous point. The live volume is mounted
read-only (protect) and the operator must reboot to recover a read-write
user-data volume. The decision to enter this posture is operator-side,
not ACT-side.

We can prove this is environmental, not user-side:

  $ touch /Volumes/UserData/Users/chistyakov/.tart-canary-write-test
    touch: cannot touch '.../.tart-canary-write-test':
        Operation not permitted

  $ touch /Users/chistyakov/Library/Caches-canary
    touch: cannot touch '/Users/chistyakov/Library/Caches-canary':
        Operation not permitted

Even outside Tart, even for non-tart files, even at /Users/chistyakov
(the firmlink not the absolute shell-visible path), every shell write to
/Volumes/UserData/Users/chistyakov/* returns EPERM. The shell-level write
call is rejected by the APFS firmware layer before any userland permission
check runs.


WHAT WOULD UNBLOCK THIS
-----------------------

The c1-c3 guest lifecycle is host-required per the ACT plan and must be run
on a host where /Volumes/UserData (or whichever volume Tart resolves $HOME
to) is mounted read-write. Concretely:

  1. Reboot the host off the Time Machine snapshot — `diskutil apfs revert`
     or a normal shutdown + restart returns /dev/disk3s8 to read-write and
     unmounts /private/tmp/snapshot. Then `tart pull` will succeed.

  2. Run this ACT from a non-TM-snapshot host. The substrate is
     host-agnostic; the same spec works on any darwin-arm64 host with a
     writable user-data volume and network egress to ghcr.io.

  3. Pre-stage the macOS base image on a writable volume using a real
     `tart pull` from a host whose user-data volume is writable, then
     `tart export` the image to a `.tvm` file and `tart import` it into
     this host's TART_HOME. This bypasses the NSURLCache write path. The
     ACT then exercises the substrate end-to-end with a pre-imported image.
     (Not attempted here because the ACT plan explicitly says "Do not build
     a custom image yet" and because no `.tvm` was available in the
     snapshot.)
