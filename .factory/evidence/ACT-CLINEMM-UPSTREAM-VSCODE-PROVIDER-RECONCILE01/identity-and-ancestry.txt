## 7. Two environment blockers found, diagnosed, and worked around (NO product change)

BLK-1 — vitest could not resolve the zod named export `z`.
  Symptom: `TypeError: undefined is not an object (evaluating 'z.enum')` in
           ../shared/src/llms/reasoning-options.ts:13, for EVERY @cline/llms suite.
  Diagnosis: the node binary bundled with the vitest 4.1.10 download was
           node v24.3.0; zod@4.4.3's ESM entry re-exports `z` in a way that
           v24.3.0's CJS-named-export detection does not pick up.  The SAME
           failure reproduces IDENTICALLY at the fork baseline
           (/private/tmp/cline-fork-baseline) => environmental, NOT a merge regression.
  Fix (environment only): put node v24.19.0 first on PATH.
  Verification: the identical command then returns
           minimax-m31-exact-id-wire01.test.ts -> 8 passed (8), exit 0.

BLK-2 — elm could not fetch the package list.
  Symptom: "PROBLEM LOADING PACKAGE LIST ... certificate has unknown CA" and
           "Your elm.json says this application needs a different version of
           Elm. It requires 0.19.2, but you are using 0.19.1".
  Diagnosis: (a) the nix-system `elm` on PATH is 0.19.1, which the repo's
           scripts/elm_toolchain.sh resolver deliberately REJECTS; the resolver
           prefers the repo-vendored /opt/homebrew 0.19.2.  (b) Elm's own HTTP
           client does not trust the system CA store; `curl` to the same URL
           returns HTTP 200, proving the network path is fine.
  Fix (environment only): SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt and
           the repo's own scripts/elm_toolchain.sh resolver.
  Verification: all 5 Elm kernels build and reproduce byte-identical SHA-256
           against their tracked .sha256 sidecars (see production-seam-map.md).

Neither blocker was "fixed" in product source.  Both are recorded as
environmental preconditions, not as ACT-owned defects.
