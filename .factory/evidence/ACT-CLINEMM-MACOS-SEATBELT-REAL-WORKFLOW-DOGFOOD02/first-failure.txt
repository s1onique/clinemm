## FIRST FAILURE (REPRODUCIBLE)

```
$ /usr/bin/sandbox-exec -p '(version 1) (allow default)' /usr/bin/true
sandbox-exec: sandbox_apply: Operation not permitted
RC=71

$ /usr/bin/sandbox-exec -p '(version 1)' /usr/bin/true
sandbox-exec: sandbox_apply: Operation not permitted
RC=71
```

The Apple Seatbelt substrate (`/usr/bin/sandbox-exec`) refuses to
apply ANY profile when invoked from this host process tree.

This was confirmed at multiple profile shapes:

  - `(version 1) (allow default)`           -> sandbox_apply EPERM
  - `(version 1)`                            -> sandbox_apply EPERM
  - production-style read+deny-network       -> sandbox_apply EPERM
  - production-style + file-write-create     -> sandbox_apply EPERM

The failure is the OUTERMOST layer (kernel sandbox-application),
not a workflow command's resource boundary.

## ROOT CAUSE

This agent's host process is itself under a macOS sandbox that
disallows nested Seatbelt application. Common causes:

  1. The agent was launched from an already-sandboxed parent
     (e.g., an automated harness that runs in an app-sandbox)
  2. SIP / AMFI / system policy explicitly disables nested
     sandbox-application for non-Apple code

This is NOT a ClineMM Seatbelt defect. The c2-green test
correctly detects "Seatbelt unavailable" via probeSeatbeltAvailability
and skips with "[c2-green] skipping: Seatbelt unavailable".

The same boundary applies to the installed ClineMM extension: when
launched from this host process tree, the experimental Seatbelt
opt-in (`CLINEMM_EXPERIMENTAL_SANDBOX=seatbelt`) becomes a no-op,
and commands fall through to the no-sandbox path.

## CONTROL vs TEST

CONTROL (no Seatbelt, normal shell):
  /usr/bin/true              -> exit 0
  /usr/bin/mktemp            -> exit 0
  git diff --check           -> exit 0
  git log --oneline -10      -> exit 0

TEST (Seatbelt attempted):
  ANY sandbox-exec invocation -> sandbox_apply EPERM at the kernel boundary

The CONTROL proves the commands themselves work. The TEST cannot
exercise the sandbox path because the host disallows nested
sandbox application.

## IS THIS A REAL SEATBELT COMPATIBILITY RED?

NO. The compatibility boundary is at the agent-environment level,
not at the ClineMM command-execution level.

The ClineMM Seatbelt backend's design correctly handles this case:

  - `probeSeatbeltAvailability()` returns false (probe fails)
  - `defaultSandboxBackendResolver("seatbelt-experimental")` returns undefined
  - `CommandJobManager.start()` falls back to no-sandbox execution
    (the disabled-default path)

The user-facing behavior is: the Seatbelt opt-in is silently a
no-op in this environment. This is "fail-safe" behavior, not
"sandbox-bypass" behavior. The user's command runs unsandboxed,
which is the default mode.
