The reviewer required a synthetic large-file test that "proves you
are no longer stuffing artifact bytes into the command line." This

Test 1: "16-MiB payload travels as stdin byte stream; bytes never enter argv"

  SIZE = 16 * 1024 * 1024 (16 MiB)
  payload = 16 MiB of pseudo-random bytes (xorshift + periodic
            non-zero markers to defeat accidental all-zero runs)
  sink   = a Bun script that reads its stdin and writes it to
            OUT_PATH. This is the stand-in for
              ssh admin@guest 'cat > /tmp/foo.vsix'

  Procedure:
    1. writeFileSync(PAYLOAD_PATH, payload)        (host side)
    2. code = await streamBytesOverSsh({           (live code path)
              cmd: ["bun", "run", SINK_PATH],
              hostBytes: payload,
              budgetMs: 30_000,
            })
    3. expect(code).toBe(0)
    4. received = readFileSync(OUT_PATH)
    5. expect(received.length).toBe(SIZE)         (no truncation)
    6. expect(received_sha256).toBe(payload_sha256) (no corruption)
    7. argvBlob = sinkCmd.join("\u0000")
    8. for 256 evenly-spaced payload bytes:
         if argvBlob.includes(byte) leaked++
    9. expect(leaked).toBeLessThanOrEqual(2)      (≤ 2/256 false-
                                                    positive ASCII
                                                    collisions only)
   10. expect(argvBlob).not.toContain(head_16_bytes)
   11. expect(argvBlob).not.toContain(tail_16_bytes)

Test 2: "streamBytesOverSsh is size-independent — no truncation at 1 KiB or 1 MiB"

  Iterates 1 KiB and 1 MiB payloads. Asserts byte-perfect

  small AND large sizes.

=========================================================================
Why this discriminates
=========================================================================

The OLD code's discriminator:

  const vsixB64 = readFileSync(args.vsixHostPath).toString("base64")
  guestExec(guestIp,
    `echo '${vsixB64}' | base64 -d > ${guestTmpPath}; ...`)

  argv would carry ~21 MiB of base64 text. On macOS, getconf ARG_MAX
  is 262144 bytes. ECHO itself has a limit (E_CHUNK) around
  ~256 KiB on macOS. The transport would fail long before
  reaching the guest — likely with `Argument list too long`
  (E2BIG from execve) or ssh failing to negotiate a channel.

The NEW code's discriminator (this test):

  streamBytesOverSsh({ cmd: sshCmd, hostBytes: payload, ... })

  cmd is fixed (~80 bytes). Bytes flow on stdin. There is no
  command-text payload to overflow. The test observes a 16-MiB
  payload transferred byte-perfectly; argv remains small and
  free of payload bytes.

If the test ever fails on a future change (regression), either
(a) the bytes entered argv (forbidden), (b) the bytes were
truncated, or (c) the SHA mismatched (corruption). All three
are loud failures.
