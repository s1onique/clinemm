## Implementation

In `apps/vscode/src/sdk/command-job-manager.ts` the `command_job_containment_failed`
emit branch (line 2460+) was extended with:

```ts
if (!job.runtimeErrorReported) {
    job.runtimeErrorReported = true
    this.reportRuntimeError({
        errorClass: "command_containment_failed",
        source: "command-job-manager",
        correlationId: job.id,
    })
}
this.emitCommandJobLifecycle({
    event: "command_job_containment_failed",
    jobId: job.id,
    pgid: typeof savedPgid === "number" ? savedPgid : undefined,
    containmentFailed: job.terminationFailed,
    jobState: "containment_failed",
    tsMs: Date.now(),
})
```

The existing `runtimeErrorReported` latch at line 2101 (the lower-level
EPERM path) and the new latch at line 2501 share the same flag. The
flow is:

  (1) terminate() -> treeResult.epermDetected && !runtimeErrorReported
      -> runtimeErrorReported := true
      -> reportRuntimeError({errorClass:"EPERM"})
  (2) finalize() -> terminalPostconditionProbe -> postcondition
      -> if postcondition != "gone" && !runtimeErrorReported
         -> runtimeErrorReported := true
         -> reportRuntimeError({errorClass:"command_containment_failed"})

ONE causal failure => AT MOST ONE runtime incident. The existing
EPERM authority wins for the EPERM-on-kill case; the new
containment_failed authority wins for the alive / unknown / pgid_unset
cases and for the EPERM-only-on-postcondition case.

In `apps/vscode/src/shared/ExtensionMessage.ts` the `RuntimeErrorClass`
union was extended additively with:

```ts
| "command_containment_failed"
```

The source taxonomy (`command-job-manager` | `run-commands-spawn`) is
unchanged; the new class is emitted from `command-job-manager` only.
