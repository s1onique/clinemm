```

## RED-A: containment failure is not visible enough

Composition today (driven by the `terminalPostconditionProbe` test seam
at command-job-manager.ts:430):

```
terminalPostconditionProbe = () => "alive"
  -> finalize() emits command_job_primary_group_cleanup(postcondition:"alive")
  -> finalize() emits command_job_residual_detected           (pre-delete, gauge)
  -> finalize() emits command_job_containment_failed          (post-delete, gauge)
  -> SdkController.handleCommandJobLifecycle(event)
        this.taskTelemetry.recordActiveCommandJobs(event.activeCommandJobs)
        // NO recordRuntimeError() call -> ! DOES NOT INCREMENT
  -> ! N stays unchanged
```

The same is true for `postcondition === "eperm"` IF the underlying
`treeResult.epermDetected === false` (i.e. EPERM only on the postcondition
probe, not on the kill). For the more typical EPERM-on-kill case the
lower-level incident was already counted at line 2101, but for the
`alive` / `unknown` / `pgid_unset` cases no incident has been counted
at all.

## RED-B: `gone` must never imply escape

Composition (no fix required — this is a CONSERVATION pin):

```
terminalPostconditionProbe = () => "gone"

  // NO command_job_residual_detected
  // NO command_job_containment_failed

This is exactly what the conservation tests (DCCT-11 in
command-job-manager-descendant-conservation.dcct01.test.ts:313) already
verify at the manager level. The new product-contract test

unchanged through the full composition.

## EPERM cardinality analysis (preliminary)

Two paths can produce a `command_job_containment_failed` event with
`containmentFailed: "substrate_eperm"`:

| Underlying `treeResult.epermDetected` | runtimeErrorReported before finalize | Required ! delta |
|--------------------------------------|-------------------------------------|------------------|
| `true`                              | `true` (latched at line 2101)       | +0 (CASE 1)     |
| `false`                             | `false`                             | +1 (new incident) |

The `job.runtimeErrorReported` latch already gates the line 2101
report. Re-using the same latch at the
`command_job_containment_failed` emit gate guarantees the
ONE-FAILURE -> ONE-! invariant.

For `alive` / `unknown` / `pgid_unset`, `runtimeErrorReported` is always
`false` at the point of `command_job_containment_failed` because no
earlier code path calls `reportRuntimeError`. These three cases are
unconditional +1.

See §6 / §12 evidence files for the wired test confirmation.
Therefore the user-visible state is:

```
ACTIVE_JOB_GAUGE          = GREEN   (^- N moves to N-1 correctly)
RUNTIME_INCIDENT_COUNTER  = WRONG   (! does NOT increment for the
                                       alive / unknown / pgid_unset paths)
```

This is the load-bearing defect this ACT must close. The fix is a
single `reportRuntimeError` call inside the
`command_job_containment_failed` emit branch, gated by the existing
`!job.runtimeErrorReported` latch so EPERM-on-kill is not double-counted
(CASE 1 per §12 of the ACT spec).
`terminate()` at line 2101, gated by `job.runtimeErrorReported`
(REC-BE-10 / REC-BE-11 verify cardinality). This is the lower-level
substrate-EPERM signal from `treeResult.epermDetected`.

The `recordRuntimeError` observer path is:

```
CommandJobManager.terminate()
  -> treeResult.epermDetected && !job.runtimeErrorReported
  -> CommandJobManager.reportRuntimeError(
       {errorClass:"EPERM", source:"command-job-manager", correlationId:job.id})
  -> options.onRuntimeError(incident)               // wired in production
  -> SdkController.handleTaskRuntimeError(incident)
  -> TaskTelemetryTracker.recordRuntimeError(incident)
  -> runtimeErrorCount += 1                          (latched on currentTaskId)
  -> webview ! N += 1
