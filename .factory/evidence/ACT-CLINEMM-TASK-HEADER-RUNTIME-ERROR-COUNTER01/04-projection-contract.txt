# Wire emission: zero-hiding single spread-conditional

apps/vscode/src/sdk/task-telemetry-tracker.ts:TaskTelemetryTracker.get()
  return {
    startedAt: ...,
    ...,
    ...(this.runtimeErrorCount > 0
      ? { runtimeErrorCount: this.runtimeErrorCount }
      : {}),
  }

A single conditional decides wire emission. When the counter is 0,
the field is OMITTED from the wire — no `runtimeErrorCount: 0` is
ever sent. This is the canonical zero-hiding pattern, matching the
existing `prevEpisodeFailures` behavior in this same getter.

# Webview normalization: single `?? 0` boundary

apps/vscode/webview-ui/src/components/chat/task-header/TaskHeaderTelemetry.tsx
  {(() => {
    const count = telemetry.runtimeErrorCount ?? 0
    if (count <= 0) return null
    const label = `${count} runtime error${count === 1 ? "" : "s"} in this task`
    return (
      <span
        aria-label={label}
        className="inline-flex items-center gap-1"
        data-testid="task-header-runtime-error-count"
        style={{ color: "var(--vscode-errorForeground)" }}
        title={label}>
        <span aria-hidden>⚠</span>
        <span className="font-mono">{count}</span>
      </span>
    )
  })()}

The webview normalizes absence via a single `?? 0` boundary. The
single `if (count <= 0) return null` is the zero-hiding rule on the
read side. Older webview bundles / Hub/Remote / Remote hosts that
don't emit the field get the same shape as `runtimeErrorCount: 0`.

# Backward compatibility

- Hub / Remote: no change to the host-side wire — they continue to
  omit `runtimeErrorCount` (it's optional). The webview renders the
  empty placeholder for them, identical to the pre-ACT behavior.
- Older webview bundles (pre-ACT): the new `runtimeErrorCount` is
  parsed-but-ignored. No regression.
- Older host with new webview: host does not emit the field, webview
  normalizes to 0, glyph stays hidden. Identical to pre-ACT behavior.
- New host with new webview: EPERM incidents surface as `⚠ N`.

# Saturated counter wire shape

Saturation at Number.MAX_SAFE_INTEGER is a defensive ceiling only.
For practical purposes, even a job that EPERMs every command would
be hard-pressed to hit even 1000 in a single session. The saturation
prevents the JS Number from accidentally incrementing past 2^53 and
producing surprising comparisons in the webview (e.g. "999" vs
"10000000000000001" looking the same to the eye but not to JSON
sort/compare).
