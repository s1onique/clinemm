### The ONE baseline test this ACT DID change — and why it was required

`cancel-liveness-diagnostic.red` went 5 passed -> 2 failed -> 5 passed.

This is NOT "changing a baseline test to inflate the pass count" (forbidden by
§9). It is the opposite: that suite's `RED-A2` and its discrimination-matrix
H-A row ASSERTED THE DEFECTIVE BEHAVIOUR IN PLACE:

```text
expect(counters.cancelPublishedCalls).toBe(0)          // RED-A2 + matrix H-A row
expect(options.postStateToWebview).not.toHaveBeenCalled()
expect(options.raiseCancelFence).not.toHaveBeenCalled()
```

i.e. the predecessor ACT deliberately pinned "with no active session, Cancel
publishes nothing and fences nothing" as the expected contract — which IS the
false-Working/Cancel defect. PTLL01's L2 repair necessarily changes that
contract, so leaving the suite untouched would have left 2 ACT-attributable
failures.

Both tests were updated to assert the REPAIRED contract, and they were made
STRONGER, not weaker — they now additionally assert that the fence raises, that
exactly one publication occurs, that the published phase is `resumable` and
explicitly NOT `completed` (Cancel must never grant completion authority), and
that no extra user prompt is dispatched (LCV-12). The `cancel-liveness-diagnostic.ts`
header matrix was updated in lockstep (`H-A` row `pub=0` -> `pub=1`) so the
documented discriminator matches the shipped behavior. `H-A` remains
distinguishable from `Healthy` and `H-B` via `acc`/`inv`/`cmp`, which all stay 0.

Verified pre-repair baseline for this suite by stashing all four production
files and re-running: **5 passed** before the repair, so the two intermediate
failures were genuinely attributable to the repair and not pre-existing.

### Classification of the pre-existing failures

Three suites fail IDENTICALLY before and after this ACT and are therefore
**not** caused by the repair:

- `background-completion-barrier01-correction04.bcb01-c4` — 3 failed / 2 passed
- `background-completion-barrier01.bcb01` — 13 failed / 1 passed
- `task-control-liveness.tcl-reach02` — 7 failed / 7 failed

Verified two independent ways: (a) `git stash push` of the repair, re-run,
`git stash pop`; and (b) `git checkout bbb5c484d -- <the 6 ACT-owned files>`
(pristine ENTRY_HEAD), re-run, `git checkout HEAD --` to restore. Both methods
produced identical pre-repair counts, and both left the repair intact.

Their root cause is recorded for the successor cursor: the `liveTools`
capability gate (`sdk-session-event-coordinator.ts:1819-1821`) was introduced
by ACT-CLINEMM-P0-COMPLETION-REEVALUATION-CAPABILITY-DISCRIMINATOR01 and
defaults to `false` when the accessor is absent. Those two suites do not wire
`liveTools`, so the Continuation Control Elm kernel returns
`fail_closed(retry_unavailable / observation_unavailable)` and the continuation
is suppressed. Wiring `liveTools: () => ["command_status", "submit_and_exit"]`
into those two harnesses was TRIED and did NOT repair them (the E3.1 deferred
barrier kernel is a separate gate), so this ACT deliberately did NOT modify
them: repairing them is a different ACT, and §9 forbids changing baseline
tests merely to improve the reported pass count.
