2) Cancel affordance
   AUTHORITY:
     - webview CommandOutputRow.tsx:178-179
         const showCancelButton =
             (isCommandExecuting || isCommandPending) &&
             typeof onCancelCommand === "function" &&
             isBackgroundExec
   PRODUCER (onCancelCommand wiring):
     - MessageRenderer.tsx:108, MessagesArea.tsx:232 both wire
         onCancelCommand={() => messageHandlers.executeButtonAction("cancel")}
     - useMessageHandlers.ts:561-580
         case "cancel":
             if (backgroundCommandRunning) {
                 await TaskServiceClient.cancelBackgroundCommand(...)
             }
             await TaskServiceClient.cancelTask(EmptyRequest.create({}))
   GAP-A:
     - isCommandExecuting is FALSE for a backgrounded command (because
       message.commandCompleted === true is hardcoded). So showCancelButton
       is FALSE. Cancel is hidden.
   GAP-B:
     - When showCancelButton is true, the cancel routes to
       executeButtonAction("cancel") → cancelTask. The background-command
       cancel is *pre-pended* to a TASK cancel. The user clicks the card
       Cancel expecting to cancel the running command; instead the entire
       task is aborted. The proto handler cancelBackgroundCommand.ts:4-9
       does not even expose a jobId parameter — it cancels all active jobs
       on the session.
   CANCELLATION TARGET AUTHORITY (already correct):
     - command-job-manager.cancel({ jobId })  (per command-status-tool.ts:191)
     - vscode-session-host.cancelBackgroundCommand(): Promise<number>
       cancels ALL active jobs on the manager
     - SdkController.cancelBackgroundCommand(): Promise<void> calls the above
   GAP-C:
     - The existing target is a session-wide cancel (no jobId filter).
       Multi-job sessions cannot cancel a single job from the UI; the
       spec calls for BGCARD-04 (Cancel dispatch carries exact jobId)
       and BGCARD-05 (two jobs preserve independent cancellation targets).
