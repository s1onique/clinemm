FIX 1 — afterEach error classifier: remove the swallowing outer catch
================================================================================

Reviewer's finding (P0-2 cleanup defect):
  "The new afterEach still contains an outer `catch {}` that swallows
   errors thrown by its inner error classifier. Its assertion that
   unknown cleanup errors are rethrown is therefore not correct."

What was wrong:
  The CORRECTION03 afterEach had:
    try {
      try {
        process.kill(-pid, "SIGKILL")
      } catch (e) {
        ...
        if (unknown error) throw e
      }
    } catch {}     // <-- this outer catch discarded the rethrow
  The docstring claimed "Unknown error: rethrow and let the test
  surface the failure" but the outer `catch {}` silently discarded
  the rethrow. Process-ownership failures were being hidden.

Fix applied:
  Removed the outer `try { ... } catch {}` wrapper. The inner
  rethrow on unknown errors now propagates and fails the test
  loudly. ESRCH and EPERM are still classified (do nothing /
  fall back to specific-PID kill), but anything else propagates.

================================================================================
FIX 2 — observePid(): single ps invocation with explicit error classification
================================================================================

Reviewer's finding (Finding 2):
  "The new test executes: ps -p ${pid} -o pid= 2>/dev/null || true
   Then interprets empty output as 'absent'. But || true suppresses
   the command's exit status. A permission failure or another ps
   error can therefore be indistinguishable from an absent process.
   There is also a race between the separate PID and status queries."

What was wrong:
  The CORRECTION03 observePid used two separate ps calls:
    1. `ps -p ${pid} -o pid= 2>/dev/null || true` -> check empty
    2. `ps -p ${pid} -o stat= 2>/dev/null || true` -> check Z
  The `|| true` suppressed ps's exit status. A permission failure
  or other ps error would produce empty output, indistinguishable
  from "process absent". The two separate calls also had a race.

Fix applied:
  Single ps invocation:
    ps -p ${pid} -o pid= stat= pgid= 2>&1; echo "__PS_RC=$?"
  The exit code is captured via the __PS_RC marker (no || true).
  The function inspects the exit code and:
    - rc != 0: throws Error with ps output (hard observation failure)
    - rc == 0 with empty stdout: returns "absent" (process gone)
    - rc == 0 with output: parses stat field, returns "zombie" or "alive"
  execSync's thrown errors (timeout, ENOENT, EACCES) are rethrown
  with the captured stderr so the test can see exactly what ps reported.
  No more silent permission-error-as-absent classification.

FIX 3 — GS-14: prove the witnessed child was alive BEFORE the timeout
================================================================================

Reviewer's finding (Finding 1, the core causal-evidence fix):
  "The report claims the process disappearing sometime after the
   five-second deadline proves that production process-group signaling
   worked slowly. It doesn't. The supplied trace shows the sleep PID
   missing from a later snapshot, while the helper itself was still
   present and its direct child appeared defunct. That chronology
   cannot establish which operation caused the disappearance."
  "Fix GS-14's observePid() to distinguish absent, alive, zombie and
   observation failure. Prove the witnessed child is alive before the
   timeout, not merely that its PID file exists afterward."

What was wrong:
  The CORRECTION03 GS-14 read the pid file AFTER the smoke response
  arrived. If the pid file contained a stale PID (one that the
  kernel had already reaped, or a never-existed PID), the test
  would still see "absent" post-timeout and pass. The witness
  did not prove the orphan was real — only that the file
  contained a number.

Fix applied:
  The test now polls the pid file in a tight loop IN PARALLEL with
  the smoke request. As soon as the file appears (the fake-tart
  writes it ~50-200ms after the helper forks it), the test:
    1. Captures the PID.
    2. Calls observePid(pid) and verifies it is "alive" or "zombie"
       (i.e., the PID was a real process in the kernel's table
       while the smoke request was still in flight).
  If the PID is "absent" at that moment, the test throws with a
  clear error: "the witness is stale; the pid file is not a
  reliable witness of a live orphan."

  This proves the witness was a real live descendant of the
  helper BEFORE the timeout. The subsequent post-timeout check
  (asserting the PID is gone within 5s) then has a meaningful
  baseline: we know the PID was alive, and now we check whether
  the production pgrp-kill reached it.
