## §0 — Frozen user-facing invariant (separated truth domains)

```text
Each token quantity in the system belongs to a SPECIFIC truth domain.
Domains are NOT additive. Conflating them produces false invariants.

REQUEST_INPUT_TOKENS
  Tokens in one actual provider-bound request.
  Source may be provider-reported exact usage OR a local estimator,
  but for any given request, exactly ONE source is authoritative.

REQUEST_OUTPUT_TOKENS
  Tokens generated by that request (model output).
  Provider-reported (preferred) or estimator-derived.

SESSION_CUMULATIVE_USAGE
  Monotonic billing/telemetry sum across all provider calls in a
  session. Compaction-generation calls (summarizer calls) count here
  if billable. NOT additive to anything else.

WORKING_CONTEXT_ESTIMATE
  Local estimate of the exact message projection about to be sent
  on the next provider request. Uses the production estimator.

COMPACTION_BEFORE_TOKENS
  Estimate/measurement of the working context immediately BEFORE
  compaction runs. Must use the SAME estimator/basis as
  COMPACTION_AFTER_TOKENS.

COMPACTION_AFTER_TOKENS
  Estimate/measurement of the resulting working context immediately
  AFTER compaction runs. Must use the SAME estimator/basis as
  COMPACTION_BEFORE_TOKENS. Must describe the actual resulting
  message projection, NOT historical billing usage.

MODEL_INPUT_BUDGET
  Effective maximum input/context budget used by compaction policy.
  Provider-specific (contextWindow, maxInputTokens, output reservation,
  hard truncation, iterative compaction, provider-side rejection, etc.).
  Recon must DISCOVER the actual final-authority seam; do NOT freeze
  "MUST abort if X" before mapping it.

CONTEXT_UTILIZATION
  WORKING_CONTEXT_ESTIMATE / MODEL_INPUT_BUDGET, or whatever exact
  production contract the recon discovers. Numerator and denominator
  MUST measure compatible quantities.

Invariants (the things we can defend):

  I1. No UI field may label SESSION_CUMULATIVE_USAGE as active context.
  I2. COMPACTION_BEFORE and COMPACTION_AFTER must measure the SAME
      semantic quantity with the SAME estimator/accounting basis.
  I3. COMPACTION_AFTER must describe the actual resulting working
      context (the next request's message projection), NOT cumulative
      historical provider usage.
  I4. Provider billing usage must remain cumulative and must NOT be
      rewritten to match context estimates.
  I5. Compaction threshold decisions must use the actual documented
      input-budget quantity, not session cumulative billing.
  I6. A displayed context/window ratio must use the same numerator and
      denominator semantics.
  I7. Estimates must be labeled/treated as estimates unless provider
      exact counts for that exact payload are available.

Common anti-patterns the recon MUST prove absent:

  - Adding SESSION_CUMULATIVE_USAGE into the working-context estimate.
  - Including summarizer-call input/output usage in the
    post-compaction working context (it belongs in the billing
    ledger only).
  - Reading "context size" from a cache that was written from a
    different estimator than the one the read uses.
  - Displaying two UI fields as if they were the same quantity
    when they are not (label ambiguity vs. arithmetic corruption).

This contract was shaped by the fresh LIVE symptom described by the
factory causal reviewer (2026-09-01) — "obviously inconsistent
compaction/context accounting" — and corrected by the factory causal
reviewer (2026-09-01) to forbid additive arithmetic across the
billing/context divide. Production delta so far: zero.
```

## §6 — Discriminator plan (R1–R3 first; R4/R5 conditional)

Do NOT author all five probes before source recon proves they correspond
to real seams. Recon first; then probably **one discriminator**.

### Primary discriminators (R1–R3)

```text
R1 — SAME-PAYLOAD ACCOUNTING

  Given an exact provider-bound message array M:

    obtain production WORKING_CONTEXT_ESTIMATE(M)

  Run the production compaction pipeline:

    M → M'

  Assert:

    COMPACTION_BEFORE_TOKENS == WORKING_CONTEXT_ESTIMATE(M)
    COMPACTION_AFTER_TOKENS  == WORKING_CONTEXT_ESTIMATE(M')

  using the ACTUAL production estimator (cited from §5).

  Assertion is on SAME-ESTIMATOR + SAME-PAYLOAD. No provider billing
  tokens are added. No provider-reported tokens from previous requests
  are added. If R1 fails, the contract violation is one of:
    - COMPACTION_BEFORE / COMPACTION_AFTER use a different estimator
      than WORKING_CONTEXT_ESTIMATE (write/read asymmetry → I2 violation)
    - COMPACTION_AFTER includes historical billing usage (I3 violation)
    - The estimator caches across estimator instances (I2 violation)
    - Provider-reported tokens from prior requests contaminate the
      working-context estimate (custom anti-pattern)

R2 — CUMULATIVE-USAGE NON-INTERFERENCE

  Keep the message array M constant across two scenarios:
    scenario A: SESSION_CUMULATIVE_USAGE = X
    scenario B: SESSION_CUMULATIVE_USAGE = X + 1_000_000

  Expected:
    WORKING_CONTEXT_ESTIMATE(M) is unchanged
    COMPACTION_BEFORE_TOKENS is unchanged
    COMPACTION_AFTER_TOKENS is unchanged
    Threshold decision is unchanged

  SESSION_CUMULATIVE_USAGE itself SHOULD differ between scenarios
  (cumulative counter is doing its job).

  R2 is likely the killer discriminator for the observed "1.1M" pathology
  if it exists in ClineMM.

R3 — REPEATED REQUEST SNAPSHOT

  Three request contexts in sequence, all distinct payloads:

    request 1 payload → working-context estimate → W1
    request 2 payload → working-context estimate → W2
    request 3 payload → working-context estimate → W3

  Expected working-context sequence:
    W1 → W2 → W3
    (each Wn corresponds to its payload; not cumulative)

  Pathology to detect:
    W1 → (W1 + W2) → (W1 + W2 + W3)
    (request-context totals are being summed across turns instead of
    snapshot per-request — the "10k → 22k → 36k" anti-pattern.)
```

### Conditional discriminators (R4/R5 — only if recon proves the seam)

```text
R4 — CACHE STALENESS
  Author ONLY if §5 (trust model) and Q11/Q12 in §4 identify a real
  cache where a token total is written by one estimator and read by
  another, or where a write is read after the underlying messages
  mutate without recomputation.

  Probe: snapshot the cached total, mutate the underlying message array
  (simulating a tool result arriving after the snapshot), assert the
  next-turn total reflects the post-mutation state.

R5 — MODEL_INPUT_BUDGET
  Author ONLY if the threshold logic reads MODEL_INPUT_BUDGET from
  hard-coded map (Q10) AND that hard-coded value disagrees with the
  canonical model metadata.

  Probe: for each model the recon identifies as drift-prone, compute
  the actual configured input budget from canonical metadata and
  assert it equals the value the threshold function uses.
```

### NOT a discriminator (deliberately)

```text
- "Compaction output must always fit under X or abort"  — too early;
  recon must DISCOVER the actual final-authority seam first. Possible
  policy shapes include: input ceiling separate from nominal context,
  reserved output budget, hard final truncation, iterative compaction,
  provider-side rejection, safety normalization. None is the answer
  before recon.

- "Summarizer-call tokens must appear in post-compaction total"  —
  this is the additive-arithmetic anti-pattern. Summarizer-call tokens
  are a billing-ledger concern, not a working-context concern.

- "Provider-billing usage must equal compaction arithmetic"  —
  same anti-pattern at the §0 level. The two ledgers are intentionally
  separate.
```
