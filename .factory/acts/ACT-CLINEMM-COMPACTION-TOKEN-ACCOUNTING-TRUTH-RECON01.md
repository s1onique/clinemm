## §0 — Frozen user-facing invariant (separated truth domains)

```text
Each token quantity in the system belongs to a SPECIFIC truth domain.
Domains are NOT additive. Conflating them produces false invariants.

REQUEST_INPUT_TOKENS
  Tokens in one actual provider-bound request.
  Source may be provider-reported exact usage OR a local estimator,
  but for any given request, exactly ONE source is authoritative.

REQUEST_OUTPUT_TOKENS
  Tokens generated by that request (model output).
  Provider-reported (preferred) or estimator-derived.

SESSION_CUMULATIVE_USAGE
  Monotonic billing/telemetry sum across all provider calls in a
  session. Compaction-generation calls (summarizer calls) count here
  if billable. NOT additive to anything else.

WORKING_CONTEXT_ESTIMATE
  Local estimate of the exact message projection about to be sent
  on the next provider request. Uses the production estimator.

COMPACTION_BEFORE_TOKENS
  Estimate/measurement of the working context immediately BEFORE
  compaction runs. Must use the SAME estimator/basis as
  COMPACTION_AFTER_TOKENS.

COMPACTION_AFTER_TOKENS
  Estimate/measurement of the resulting working context immediately
  AFTER compaction runs. Must use the SAME estimator/basis as
  COMPACTION_BEFORE_TOKENS. Must describe the actual resulting
  message projection, NOT historical billing usage.

MODEL_INPUT_BUDGET
  Effective maximum input/context budget used by compaction policy.
  Provider-specific (contextWindow, maxInputTokens, output reservation,
  hard truncation, iterative compaction, provider-side rejection, etc.).
  Recon must DISCOVER the actual final-authority seam; do NOT freeze
  "MUST abort if X" before mapping it.

CONTEXT_UTILIZATION
  WORKING_CONTEXT_ESTIMATE / MODEL_INPUT_BUDGET, or whatever exact
  production contract the recon discovers. Numerator and denominator
  MUST measure compatible quantities.

Invariants (the things we can defend):

  I1. No UI field may label SESSION_CUMULATIVE_USAGE as active context.
  I2. COMPACTION_BEFORE and COMPACTION_AFTER must measure the SAME
      semantic quantity with the SAME estimator/accounting basis.
  I3. COMPACTION_AFTER must describe the actual resulting working
      context (the next request's message projection), NOT cumulative
      historical provider usage.
  I4. Provider billing usage must remain cumulative and must NOT be
      rewritten to match context estimates.
  I5. Compaction threshold decisions must use the actual documented
      input-budget quantity, not session cumulative billing.
  I6. A displayed context/window ratio must use the same numerator and
      denominator semantics.
  I7. Estimates must be labeled/treated as estimates unless provider
      exact counts for that exact payload are available.

Common anti-patterns the recon MUST prove absent:

  - Adding SESSION_CUMULATIVE_USAGE into the working-context estimate.
  - Including summarizer-call input/output usage in the
    post-compaction working context (it belongs in the billing
    ledger only).
  - Reading "context size" from a cache that was written from a
    different estimator than the one the read uses.
  - Displaying two UI fields as if they were the same quantity
    when they are not (label ambiguity vs. arithmetic corruption).

This contract was shaped by the fresh LIVE symptom described by the
factory causal reviewer (2026-09-01) — "obviously inconsistent
compaction/context accounting" — and corrected by the factory causal
reviewer (2026-09-01) to forbid additive arithmetic across the
billing/context divide. Production delta so far: zero.
```
